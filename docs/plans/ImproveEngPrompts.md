# Engineering-Prompt Improvement Recommendations

> Working/local doc — gitignored. Not committed. Generated by reviewing
> [`addyosmani/agent-skills`](https://github.com/addyosmani/agent-skills) (21 senior-engineering skill modules)
> against this codebase's 114 prompt templates and recent regression patterns from `LessonsLearned.md`.

## Framing principle

VirtualDevTeam already has the right shape (role-driven prompts, multi-agent coordination, gate-based workflow).
What it lacks is **discipline-shaped prompt fragments** that encode senior-engineer habits — _how_ to reason,
not _what_ role to play. We do **not** need a parallel skill-discovery framework, and we do **not** need
slash commands. We need small fragments included from the existing role prompts, plus targeted in-place
tweaks to the heaviest prompts.

Hard constraints applied throughout:

- Total new prompt lines target ≤ 800 across all recommendations.
- New files only when a discipline is truly cross-cutting (used by ≥ 2 roles).
- Every recommendation cites a concrete prompt path or LessonsLearned entry.
- No new prompt-loading framework, no slash commands, no parallel skill index.
- This doc is gitignored — it's a working artifact, not a committed spec.

## 2. In-place tweaks (medium-to-high impact)

### Tweak 4 — Promote vertical-slice principle in plan-generation-system.md

**Target:** `prompts/software-engineer/plan-generation-system.md` (lines 22-32)

**Why:** Vertical slicing is currently a single bullet at line 57 buried among 6 other bullets. Engineers consistently produce horizontal-layer plans (T1 = all models, T2 = all services, T3 = all UI). This is the #1 cause of "T1 does too much" + merge conflicts.

**Add at top of "Task Sizing Strategy" section (right after `## CRITICAL — Task Sizing Strategy`):**

```markdown
> **Top-priority rule: vertical slices over horizontal layers.** Each task must
> be a thin top-to-bottom slice through the stack (data + service + UI + tests
> for ONE feature) — never a horizontal cut (e.g., "all models" then "all
> services"). A user must be able to demo the slice end-to-end after merge.
> Horizontal-layer plans cause merge conflicts, broken intermediate states,
> and force every other engineer to wait for a layer to finish. If you're
> tempted to split by layer, stop and re-slice by feature.
```

**Expected effect:** Reduces "T1 does everything" + reduces 2nd/3rd-task merge conflicts. Estimated −1 rework cycle per project on average.

### Tweak 5 — Expand `engineer-base/self-assessment-system.md` with 3 new axes

**Target:** `prompts/engineer-base/self-assessment-system.md` ("What to Check" section, lines 24-30)

**Why:** Currently checks only AC coverage and file completeness. Misses (a) end-to-end run-ability, (b) simplicity, (c) accidental over-delivery / scope creep. Lessons Learned #14 confirms self-assessment must run on both base and SE-direct paths — when it runs, it should be thorough.

**Replace the "What to Check" section with:**

```markdown
## What to Check

- **Acceptance criteria coverage:** Each criterion from the Issue should have code that implements it
- **File completeness:** All files mentioned in the task's File Plan should exist and have real content
- **No placeholders:** No "TODO", "placeholder", "lorem ipsum", or stub implementations for required features
- **Scope compliance:** Only files in the task scope should be modified — no accidental changes to shared infrastructure
- **Functional coherence:** Components should wire together (imports resolve, routes exist, DI registrations present)
- **Build & run sanity:** Run the build (or note that you did, and what it reported). If the slice is user-facing, confirm the page/component loads without error in the workspace.
- **Simplicity:** For each non-trivial file you wrote, ask "would a junior engineer understand this in <30s?" Flag any clever-but-dense code, gratuitous abstractions, or premature generalization (one use site = inline; ≥3 use sites = extract).
- **Scope discipline:** If you implemented anything not explicitly in the AC list, call it out. Bonus features = scope creep, even if they "seem nice."
```

**Expected effect:** Catches `LessonsLearned #14`-class issues (SE bypassing self-assessment), reduces over-built T1s, and surfaces accidental scope expansion before peer review.

### Tweak 8 — Force 5-axis grid in code review prompts

**Target:** `prompts/software-engineer/code-review-system.md`, `prompts/architect/pr-review-system.md`

**Why:** Current review prompts ask for prose feedback. Reviewers default to readability nits and skip security/performance. Forcing a structured grid keeps reviewers honest.

**Insert into review prompt (just before the output format section):**

```markdown
## Required Review Axes (all five — do not skip any)

For each axis, output a one-paragraph assessment AND a 1–10 score. Scores below 7 must include a specific reason and a concrete suggested fix.

1. **Correctness** — does it match the spec? Edge cases? Error paths? Race conditions? Off-by-ones?
2. **Readability & simplicity** — could a junior engineer understand it in <30s? Clever tricks that should be simplified? Names descriptive? Dead code or no-op variables?
3. **Architecture** — fits existing patterns? Clean module boundaries? No circular deps? Abstraction level appropriate (not over- or under-engineered)?
4. **Security** — input validation? Parameterized queries? Output encoding? Secrets out of code? See `_shared/security-checklist.md` if present.
5. **Performance** — N+1? Unbounded loops? Sync-when-async? Missing pagination? Avoidable re-renders?

**Approval standard:** Approve when the change definitely improves code health, even if not perfect. Don't block on style preferences. Do block on any axis scoring ≤ 5.
```

**Expected effect:** Catches the "review found 2 readability nits but missed the SQL injection" failure mode. Aligns with addyosmani's "perfect doesn't exist; continuous improvement" approval standard.

### Tweak 2a — PM Spec assumption surfacing

**Target:** `prompts/pm/single-pass-spec.md`

**Why:** PMSpec.md template has a "Constraints & Assumptions" section but the prompt doesn't require the PM to flag _ambiguous_ assumptions vs _given_ assumptions. PM silently fills gaps the wizard didn't catch.

**Add as a new section just before "## Executive Summary" generation:**

```markdown
## Surface Ambiguous Assumptions FIRST

Before writing any spec content, list 3–8 assumptions you are about to make where the project description left ambiguity. Format each as a one-liner with the resolution you're picking and the alternative you're rejecting. Place these in `## Constraints & Assumptions` under a sub-heading `### Ambiguity Resolutions Made During Spec`. The Architect and SE will see these and can challenge them.

Example:
- **Persistence model:** Picked browser-only localStorage. Rejected server-side persistence (no auth in scope per project description). Revisit if checklist progress sync becomes a requirement.
- **Branding:** Picked generic enterprise-styled. Rejected org-specific identity (no logo/color guide provided).

Do NOT proceed to write user stories or acceptance criteria until these ambiguity resolutions are listed. Each downstream story should reference any assumption it depends on.
```

**Expected effect:** Architect/SE no longer waste rework cycles on "but I assumed X" loops. Aligns with addyosmani's "don't silently fill in ambiguous requirements" rule.

### Tweak 9 — TDD framing in test-engineer

**Target:** `prompts/test-engineer/single-pass-system.md`, `prompts/test-engineer/tier-system-base.md`

**Why:** TE prompts are reactive — they generate tests after the engineer ships. Adding "prove-it-first" framing reduces flaky / weak / tautological tests.

**Insert at the top of `single-pass-system.md`:**

```markdown
## Tests are proof, not paperwork

Every test must answer "what would break if this code regressed?" Two rules:

1. **Tests-as-spec:** Read the AC list before reading the code. The test names should mirror AC items, NOT implementation details. If you can't write a test name without reading the implementation, you're testing the implementation, not the contract.
2. **Bug-fix tests must fail without the fix:** If you're regression-testing a bug fix, mentally (or actually) revert the fix and confirm your test fails. A test that passes against the bug isn't a regression test — it's an alibi.
```

**Expected effect:** Reduces tautological tests (`expect(getThing()).toEqual(getThing())`), reduces "looks tested but isn't" coverage.

### Tweak 10 — Browser devtools verification in tier-ui-guidance

**Target:** `prompts/test-engineer/tier-ui-guidance.md`

**Why:** Playwright tests fire and pass even when the page emits console errors, network 5xx, or a11y violations. addyosmani's `browser-testing-with-devtools` skill captures the discipline of asserting absence of errors as part of every UI test.

**Add a new section near the top:**

```markdown
## Console & Network assertions are mandatory

Every UI test must assert **absence of unexpected runtime errors**, not just presence of expected DOM. Add to each Playwright test:

```typescript
const consoleErrors: string[] = [];
const networkFailures: string[] = [];
page.on('console', m => { if (m.type() === 'error') consoleErrors.push(m.text()); });
page.on('response', r => { if (r.status() >= 500) networkFailures.push(`${r.status()} ${r.url()}`); });
// ... test body ...
expect(consoleErrors, `console errors: ${consoleErrors.join('\n')}`).toHaveLength(0);
expect(networkFailures, `5xx responses: ${networkFailures.join('\n')}`).toHaveLength(0);
```

When asserting visible content, prefer `getByRole` / `getByLabel` over `getByText` so accessibility regressions surface as test failures.
```

**Expected effect:** Captures the silent-failure case where the page rendered fine but threw a 500 in the background.

### Tweak 12 — ADR-style decision capture for architect

**Target:** `prompts/architect/full-system.md`, `prompts/architect/multi-turn-decisions.md`

**Why:** Architecture.md captures decisions but rarely the alternatives considered or why they were rejected. When SE rework happens, the architect can't reload context to defend the original choice — leading to flip-flop decisions across rework cycles.

**Add to architect guidance:**

```markdown
## Each significant decision: capture as a 4-line ADR

For every architectural choice that has a plausible alternative, document it in this format:

```
### ADR-N: <decision title>
- **Decision:** <what we chose>
- **Alternatives rejected:** <list, one line each>
- **Rationale:** <why this fits the spec/constraints better>
- **Reversible if:** <what would have to change to re-open this>
```

Examples of decisions worth ADR-capturing: state management library choice, persistence layer, auth strategy, rendering model (SSR vs CSR vs SSG), test framework, package manager. Skip ADRs for trivial choices (folder names, formatter config).
```

**Expected effect:** Rework cycles stay anchored. Reviewers and engineers don't relitigate decisions because the rationale is preserved.

### Tweak 13 — Idea-refine iteration in wizard

**Target:** `prompts/wizard/clarifying-questions.md`, `prompts/wizard/clarifying-questions-more.md`

**Why:** Wizard collects 10 answers and stops. Vague answers ("yes, generally") get baked into the spec as if they were precise. addyosmani's `idea-refine` skill iterates until answers are concrete.

**Add to clarifying-questions.md:**

```markdown
## When a user's answer is vague, follow up — don't just record it

For each answer, classify:
- **Concrete:** specific (e.g., "Yes, store in localStorage with 30-day expiry"). Accept.
- **Vague:** non-specific (e.g., "Yes, generally", "It depends", "Maybe"). Trigger one follow-up that names the most likely sub-question, like: "When you say 'generally', do you mean (a) always, (b) only for logged-in users, or (c) only on the readiness checklist page? Pick one or describe."

Cap at one follow-up per question to avoid wizard fatigue. If the second answer is still vague, record it AS vague in the resulting spec under "Ambiguity Resolutions Made During Spec" so PM can flag it.
```

**Expected effect:** Higher-quality PMSpec.md, fewer "I'll just guess" moments downstream.

### Fragment 1 — `prompts/_shared/triage-on-failure.md` (~80 lines)

**Included from:** `engineer-base/build-fix.md`, `engineer-base/build-fix-cli-edit.md`, `engineer-base/rework-system.md`, `engineer-base/rework-system-cli-edit.md`, `test-engineer/build-fix-inline-system.md`, `test-engineer/workspace-build-fix-system.md`

**Content** (full file):

```markdown
---
description: "Stop-the-line triage discipline for build/test/runtime failures"
tags: [shared, debugging, triage]
---

## Triage discipline — DO THIS BEFORE making any code change

When a build fails, test fails, or runtime behavior is unexpected:

### Step 1: STOP
Do NOT add new features, do NOT make speculative fixes, do NOT skip ahead. The cheapest bug to fix is the one you fix BEFORE building on top of it.

### Step 2: PRESERVE the evidence
Before doing anything else, record:
- The exact error message (verbatim, not paraphrased)
- The exact command that triggered it
- The last code change you made (file + brief description)
- The state of the workspace (clean? mid-edit? what's modified?)

### Step 3: REPRODUCE reliably
Can you reproduce the failure on demand?
- ✅ YES → proceed to Step 4
- ❌ NO → it's flaky. Run the failing command 3-5 times. Note the success rate. If <100%, treat as a race condition / timing issue (do NOT mark as "fixed" without a regression test that consistently fails before the fix).

### Step 4: FORM A HYPOTHESIS — write it down before fixing
"I think the failure is caused by X because Y. If I'm right, fixing X by doing Z will resolve it. If I'm wrong, the failure will persist or change shape."

This single sentence prevents the "fix-by-guessing" anti-pattern that drives multi-cycle rework loops.

### Step 5: FIX the root cause, not the symptom
- ❌ Symptom fix: catch the exception silently, increase the timeout, comment out the failing test.
- ✅ Root-cause fix: understand WHY the exception was thrown, why the timeout was needed, why the test fails.

If you cannot identify a root cause within ~5 minutes of investigation, the right move is to add diagnostic logging and re-run — NOT to apply a speculative fix.

### Step 6: GUARD against recurrence
Either (a) add a test that fails without your fix and passes with it, or (b) document in the PR description why this case is impossible to regression-test (e.g., timing-dependent race that can't be deterministically reproduced).

### Anti-patterns to avoid

- **Skip-ahead fix:** "I'll fix this and the next thing too." → No. One root cause at a time.
- **Symptom-only fix:** Catching an exception without understanding it. → No.
- **Test-removal fix:** Deleting or skipping the failing test. → Forbidden unless the test itself is wrong AND you document why.
- **Multi-fix mega-commit:** Bundling 5 unrelated fixes. → No. One commit per root cause.
- **"Should be fine":** Pushing a fix without re-running the failing command. → Always re-verify.
```

**Wire-in:** In each target prompt, add at the very top: `{{> triage-on-failure}}`. Existing rework/build-fix logic stays intact below.

**Expected effect:** Reduces rework-cycle count from average 2.x → 1.x by making engineers actually diagnose before patching. Aligns with `MaxReworkCycles=2` config — if we hit cycle 2, the cost is high.

### Fragment 2 — `prompts/_shared/code-simplicity-self-check.md` (~70 lines)

**Included from:** `engineer-base/self-assessment-system.md` (in addition to Tweak #5), `software-engineer/code-review-system.md`, `architect/pr-review-system.md`

**Content** (full file):

```markdown
---
description: "Reviewer-style simplicity check — flag overcomplexity before it ships"
tags: [shared, review, simplicity]
---

## Simplicity rubric — apply before approving any change

The goal is NOT fewer lines. The goal is code that a new contributor can understand without explanation.

### The five tests

1. **Same-output test:** Does the simpler version produce the same output for every input, the same error behavior, and the same side effects? If unsure, don't simplify.
2. **Convention test:** Match the project's existing patterns (naming, imports, error handling). Inconsistency-creating "simplification" is just churn.
3. **Clarity-over-cleverness test:** Explicit code beats compact code when the compact version requires a mental pause to parse. (Dense ternary chains, chained reduces with inline closures, magic numbers — all flagged.)
4. **Abstraction-earning test:** Don't generalize until the third use case. Premature abstraction is harder to remove than to add.
5. **Dead-code test:** Any unused imports, unreachable branches, no-op variables (`_unused = …`), backwards-compat shims with no consumers, or `// removed` comments? All must go.

### Quick anti-pattern checklist

- ❌ A 500-line file where 100 would suffice
- ❌ A class with one method (should be a function)
- ❌ An interface with one implementation (should be the class itself, until ≥2 impls exist)
- ❌ A configuration system for a value that has never changed
- ❌ Defensive null checks for values the type system says are never null
- ❌ "Util" / "Helper" / "Manager" classes that grow without bound (split or inline)
- ❌ Comments that restate what the code obviously does (delete; only keep WHY-comments)
- ❌ TODO / FIXME / XXX comments without a tracking issue (delete or file the issue)
- ❌ `try { ... } catch (e) { /* ignore */ }` (always log or rethrow)

### Output

If reviewing: list each violation as `[Simplicity #N]` with file:line and the concrete fix.
If self-assessing: count violations. If ≥3, flag for simplification before publishing.
```

**Wire-in:** In `engineer-base/self-assessment-system.md`, add to the "What to Check" section: `Simplicity (see {{> code-simplicity-self-check}})`. In review prompts, embed via `{{> code-simplicity-self-check}}`.

**Expected effect:** Reduces "T1 ships 1000 lines for what 200 would do" pattern. Direct counter to the heaviest LessonsLearned anti-pattern (over-built foundation tasks).

### Fragment 3 — `prompts/_shared/context-engineering.md` (~60 lines)

**Included from:** `engineer-base/single-pass-implementation.md`, `engineer-base/step-implementation-system.md`, `software-engineer/implementation-system.md`, `specialist-engineer/implementation-system.md`

**Content** (full file):

```markdown
---
description: "Context budget guidance — what to read, how deep, when to stop"
tags: [shared, context, engineering]
---

## Context discipline — read what matters, ignore what doesn't

The agent that reads everything wastes tokens and loses focus. The agent that reads nothing hallucinates APIs and misses conventions. Find the middle.

### Read first (always, every task)

1. **Project rules:** `.github/copilot-instructions.md` or `AGENTS.md` (already in your context).
2. **The task issue body** in full — including AC list and File Plan.
3. **Architecture.md and PMSpec.md** — at least the sections relevant to your task. (Skim, don't deep-read.)
4. **Existing files in your File Plan** — every file you're going to modify, in full.

### Read on demand (only when you need it)

- **A neighbor file** — when your task imports or extends something from it, read enough to copy the pattern.
- **A test file** — when you change behavior, find the test that covers it. If none exists, plan to add one.
- **Project config** (csproj, package.json, tsconfig) — only when adding a dependency or changing a build setting.

### Skip unless cited

- **Sibling tasks' files** — they're not yours; touching them creates merge conflicts.
- **Generated files** (bin/, obj/, dist/, *.g.cs, lockfiles) — never read or modify.
- **Docs unrelated to your task** — README sections about deployment, contribution, etc.
- **Old commits / PRs** — unless you're explicitly debugging a regression introduced recently.

### Stop signal — when to halt context-loading

If you have read >5 files and you're still not sure what to write, the issue is likely scope ambiguity (see `pre-pr-questions.md`), NOT missing context. Asking a clarifying question is cheaper than reading 10 more files.

### Token-budget heuristics

- A typical SE task should fit in <30K tokens of read context. If you're past that, you're probably reading too much.
- For each file you read, ask: "what one fact am I extracting?" If you can't name it, you're skimming.
- Prefer reading the smallest file that demonstrates the pattern over the largest file that uses it.
```

**Wire-in:** Embed via `{{> context-engineering}}` near the top of engineer implementation prompts, after the role description.

**Expected effect:** Reduces token burn (LessonsLearned alludes to token tracking). Reduces "agent read 50 files but missed the convention in the one neighbor file" failure mode.

### Fragment 4 — `prompts/_shared/security-checklist.md` (~70 lines)

**Included from:** `software-engineer/code-review-system.md`, `architect/pr-review-system.md`, `engineer-base/single-pass-implementation.md` (only when task touches user input / auth / external IO)

**Content** (full file):

```markdown
---
description: "OWASP-aligned security checklist for web features"
tags: [shared, security]
---

## Security checklist — apply when the change touches user input, auth, or external IO

Skip this fragment for changes that touch only static content, internal tooling, or test infrastructure.

### Always do

- **Validate all external input at the boundary.** API routes, form handlers, query string parsers, file upload handlers, webhooks.
- **Parameterize database queries.** Never concatenate user input into SQL/NoSQL/OS commands.
- **Encode output.** Use the framework's auto-escape (Razor's `@`, React's JSX). Don't bypass with `MarkupString`, `dangerouslySetInnerHTML`, or `innerHTML = userValue`.
- **Use HTTPS** for any external communication.
- **Hash passwords** with bcrypt/scrypt/argon2. Never plaintext, never base64, never custom.
- **Set security headers:** CSP, HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy.
- **Use httpOnly + secure + sameSite cookies** for sessions.
- **Treat external data as untrusted** — even from "trusted" partners.

### Ask before doing (don't just ship)

- New auth flow or auth-logic change.
- New category of sensitive data (PII, payment, biometric).
- New external service integration.
- CORS configuration changes.
- File upload endpoints.
- Rate-limit / throttling changes.
- Any code that grants elevated permissions.

### Never do

- ❌ Commit secrets to version control. (`appsettings.json` is tracked — use `dotnet user-secrets` or env vars per `.github/copilot-instructions.md`.)
- ❌ Log passwords, tokens, full payment numbers, or other PII in plain text.
- ❌ Trust client-side validation as a security boundary.
- ❌ Disable security headers "for testing" — use a test-only env override instead.
- ❌ `eval()` or `innerHTML` with user-provided data.
- ❌ Store auth tokens in localStorage (use httpOnly cookies).
- ❌ Expose stack traces to users (log them server-side, return a generic error).
- ❌ Create users / change passwords / send emails as a side effect of a GET request.

### Quick OWASP-Top-10 self-check before publishing

- [ ] Injection — all DB queries parameterized, no shell-out with user input
- [ ] Broken Auth — sessions short-lived, password reset flows verified
- [ ] Sensitive Data Exposure — no PII in logs, HTTPS-only
- [ ] XXE — XML parsing disables external entities (or uses JSON)
- [ ] Broken Access Control — every protected endpoint checks authz
- [ ] Security Misconfiguration — default creds removed, debug-mode off in prod
- [ ] XSS — output encoded, CSP set
- [ ] Insecure Deserialization — no `BinaryFormatter`, no `pickle.loads(untrusted)`
- [ ] Components with Known Vulns — dependencies auditable
- [ ] Insufficient Logging — auth failures + admin actions logged

If your change is a static site or pure local-only HTML (e.g., the current Compliance Compass project description), you can skip OWASP and apply only "Never do" — no eval/innerHTML, no localStorage for secrets.
```

**Wire-in:** Trigger inclusion conditionally — `single-pass-implementation.md` adds `{{> security-checklist}}` ONLY when the task description / file plan touches `auth | login | password | input | upload | api | endpoint | session`. Code-review prompts include unconditionally.

**Expected effect:** First-pass catches for the obvious vulns. Catches `appsettings.json` secret regressions before commit.

### Fragment 5 — `prompts/_shared/api-interface-contract.md` (~50 lines)

**Included from:** `software-engineer/plan-generation-system.md` (T-FINAL integration task), `architect/multi-turn-components.md`, `software-engineer/implementation-system.md` (only when task creates a service / API surface)

**Content** (full file):

```markdown
---
description: "Lock interface contracts before implementation"
tags: [shared, api, design]
---

## Interface-first discipline

When the task creates a new service, API, public class, or shared module, define the contract BEFORE writing the implementation. The contract is the spec.

### Contract checklist

For each public method / route / component prop:
- **Inputs:** types, required vs optional, validation rules.
- **Outputs:** types, success shape, error shape.
- **Error contract:** thrown exceptions / error codes / status codes that consumers can rely on.
- **Idempotency:** safe to call twice with the same input?
- **Side effects:** what state changes, what events emit, what gets logged.

### Hyrum's-law guardrail

> Every observable behavior — including error message text, response timing, and ordering — becomes a de facto contract once consumers depend on it.

Implications:
- Don't expose internal implementation details in error messages.
- Don't promise ordering you don't intend to keep (use unordered Set/Dict at boundaries).
- Don't leak stack traces to API responses.
- Plan for deprecation: every public surface needs a removal/migration path.

### Anti-patterns

- ❌ "I'll figure out the return type as I implement." → Define the type up front. Refactoring a return type is 10x harder after consumers exist.
- ❌ "Errors will throw a generic Exception." → Use a typed error hierarchy that consumers can catch selectively.
- ❌ "I'll keep this private for now." → If `T-N+1` will need it, make it `internal`+visible-to-test. If two engineers need it, it's already public-shaped.
- ❌ Two methods that do "almost the same thing" with different parameter orders. → Pick one canonical form.

### Output

Before writing implementation code:
1. Sketch the contract as TypeScript-style or C#-style interface declarations.
2. List the 2-3 most important error conditions and how they're surfaced.
3. THEN implement. The contract is now your spec.
```

**Wire-in:** Reference from architect prompts and SE implementation prompts when the task description includes service / api / interface / contract keywords.

**Expected effect:** Reduces "rewrote the API on day 3" thrash. Forces error-contract design (currently absent).

### Fragment 6 — `prompts/_shared/performance-checklist.md` (~50 lines)

**Included from:** `software-engineer/code-review-system.md`, `architect/pr-review-system.md`. Optional inclusion in implementation prompts when task touches lists / queries / loops over large data.

**Content** (full file):

```markdown
---
description: "Quick performance checklist — catch obvious misses pre-merge"
tags: [shared, performance]
---

## Performance checklist — apply during review and self-assessment

This is NOT a profiling guide. It's a list of obvious mistakes to catch before merge.

### Database / external calls

- [ ] No N+1 queries (one parent → N child fetches in a loop). Use joins / eager loading / batched lookups.
- [ ] List endpoints have pagination. (Default page size, max page size, cursor or offset.)
- [ ] Queries have indices on the columns they filter / sort on.
- [ ] Don't `SELECT *` when you need 3 columns. Don't load 1000 rows when you display 20.

### Loops & data structures

- [ ] No unbounded loops on user input. (Cap iteration count or input size.)
- [ ] No O(n²) when O(n log n) is trivial (e.g., sort once instead of `Contains` in a loop — use a HashSet/Dictionary).
- [ ] No re-iterating the same collection inside a loop body.

### Async / I/O

- [ ] Network calls / file I/O are async (not sync-on-async-stack).
- [ ] Don't `Task.Result` / `.Wait()` on hot paths — leads to deadlocks and thread starvation.
- [ ] Don't fire 100 parallel API calls in a `Promise.all` without rate limiting / batching.

### UI / rendering

- [ ] Lists with >50 items use virtualization (or pagination).
- [ ] Components don't re-render the whole tree on every keystroke (memoize / use `key` props correctly).
- [ ] Images are sized appropriately (no 4MB hero images).
- [ ] Don't fetch on every render (use stable cache keys).

### Memory

- [ ] Event listeners are removed on cleanup / disposal.
- [ ] No closures capturing large objects unnecessarily.
- [ ] Streaming responses where the response could be >1MB.

### Output

If reviewing: flag any violation as `[Perf #N]` with file:line + the concrete fix.
If self-assessing: any violation = "needs simplification before publish".

If your task is a static site / local-only / small-data-volume, perf checks are mostly N/A — focus only on the UI / rendering / memory rows.
```

**Wire-in:** Include in review prompts. Implementation prompts include it conditionally based on task type.

**Expected effect:** Catches obvious misses (the Compliance Compass static site won't trigger most rows, but a future API-heavy project would).

```markdown
---
description: "Security auditor reviewer persona — only activates for security-sensitive changes"
variables:
  - tech_stack
tags: [persona, security-auditor]
---

You are a Security Auditor reviewing a pull request for security defects. You do NOT review style, architecture, or readability — only security. The project uses {{tech_stack}}.

## Your scope

You review ONLY when:
- The PR title or body mentions auth, login, password, token, session, OAuth, JWT, API key, secret, encryption, hash, sanitiz, validat, upload, file, parse, XML, JSON parsing.
- OR the PR has the `security-sensitive` label.
- OR the change touches `appsettings.json`, `develop-settings.json`, `.env`, or any other config file that could contain secrets.

For all other PRs, you respond with `{ "applicable": false }` and exit.

## What you check

Apply the OWASP Top 10 and the `_shared/security-checklist.md` rules. For each finding:
- **Severity:** critical / high / medium / low
- **Category:** OWASP-A0X classification
- **Location:** file:line
- **Issue:** one-sentence description
- **Suggested fix:** concrete code change

## Output format

```json
{
  "applicable": true | false,
  "findings": [
    { "severity": "high", "category": "A03 Injection", "location": "src/Controllers/UserController.cs:42", "issue": "User input concatenated into SQL query", "fix": "Use parameterized query: db.Users.Where(u => u.Email == email)" }
  ],
  "approval": "approve | block | escalate",
  "summary": "<one-line summary>"
}
```

## Approval rules

- 0 findings → approve.
- Only low/medium findings → approve with notes.
- Any high or critical → block.

## Anti-patterns to avoid (your own conduct)

- Don't review for style or architecture — that's the SE/architect's job.
- Don't approve based on "should be fine" — verify the fix or block.
- Don't suggest fixes that introduce new attack surface.
- Don't ignore secrets in logs / error messages just because the test environment is local.
```

## 8. Rollout sequencing — how to ship safely

1. **Don't merge all 15 at once.** Roll Wave 1 first (in-place tweaks) — those carry zero file-creation risk and 80% of the value.
2. **Hot-reload friendly.** All edits are to `prompts/*.md` files; `PromptTemplateService.HotReload=true` (per `appsettings.json`) — no Runner restart required.
3. **Fragments folder.** Create `prompts/_shared/` if it doesn't exist. Confirm `PromptTemplateService` can resolve `{{> _shared/<name>}}` includes. If not, fall back to flat `prompts/shared-<name>.md`.
4. **A/B comparison.** For each major change, capture a "before" PMSpec.md / EngineeringPlan.md / SE PR diff with the current prompts. After rollout, capture the "after". Side-by-side, the recommendations either stand on their own or don't.
5. **Reverse-easily principle.** Each tweak is a self-contained block of text; reverting any one is a `git revert <commit>`. No cross-prompt dependencies introduced.
